- TypeScript и ESLint: без ошибок.
- Автоматические тесты: 9 из 9 пройдены.
- Production-сборка Vite: успешно.
- Сервер разработки и просмотр готовой сборки запущены из итоговой папки и открыты в браузере. На экране подключения ошибок консоли нет; неверный `idInstance` отклоняется до запроса API.
- В браузере с подменёнными ответами API проверены: ошибка доступа, валидация номера, создание и повторный выбор чата, отправка и получение текста, переносы строк и emoji, лимит 4000 символов, сохранение текста после ошибки отправки, отдельные черновики двух чатов.
- Проверены настольный интерфейс и мобильная ширина 390 px, возврат к списку чатов и отсутствие горизонтального переполнения.
- Проверены выход с непустым черновиком, очистка формы подключения, пустой список чатов после повторного входа и сброс сессии при обновлении страницы.

24 сентября 2026 года сквозной сценарий проверен с действующим инстансом MAX: сообщение отправлено методом SendMessage, доставлено получателю, ответ получен через HTTP API и отображён в нужном чате. Работа с опубликованного домена пока не проверялась.

## Автоматические проверки

Команды для воспроизведения:

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run build
```

Тесты используют подменённые HTTP-ответы. Они не отправляют сообщения в MAX.

## Ручной сценарий с реальным MAX

Для полной проверки нужны авторизованный инстанс GREEN-API MAX и второй аккаунт получателя. Реальные данные доступа не входят в проект.

1. Запустить приложение и открыть его в браузере.
2. Проверить пустые поля, неверный `idInstance` и ошибочный токен: соединение не должно открываться, причина ошибки должна быть видна.
3. Ввести рабочие `idInstance`, `apiTokenInstance` и `apiUrl` из кабинета. Дождаться открытия списка чатов.
4. Создать чат по номеру получателя. Неверный номер отклоняется; отсутствующий аккаунт вызывает понятную ошибку. Повторный ввод уже добавленного номера открывает тот же чат.
5. Отправить обычный текст, сообщение с переносом строки и сообщение с emoji. Проверить их появление на телефоне получателя. Пустое сообщение и текст длиннее 4000 символов не отправляются.
6. Ответить с телефона, в том числе текстом со ссылкой. Убедиться, что ответ появился один раз в правильном чате.
7. Создать второй чат, оставить разные черновики и переключиться между ними. Черновики и сообщения не должны смешиваться.
8. Отключить интернет: ошибка получения должна появиться без потери переписки. Восстановить интернет и дождаться возобновления получения. Не повторять отправку после таймаута, пока не проверено, пришло ли сообщение на телефон.
9. Проверить окно шириной 390 px: открыть чат, вернуться стрелкой к списку и снова выбрать чат. Поле ввода и кнопка отправки должны быть доступны.
10. Выйти: должны очиститься ключ, чаты и черновики, а запросы получения — прекратиться. Повторить проверку с обновлением страницы.

При отсутствии входящих ответов проверить `incomingWebhook`, пустой `webhookUrl` и отсутствие второго потребителя очереди. При отказе `CheckAccount` проверить доступность поиска по номеру в настройках приватности получателя и ограничения тарифа/аккаунта.

## Перед публикацией

- Сохранить `package-lock.json` вместе с исходниками.
- Не добавлять токен, `.env.local`, `node_modules` и `dist` в Git.
- Разместить сборку `dist` на HTTPS-хостинге и повторить реальный сценарий с опубликованного адреса.
- Сделать скриншоты или короткое видео реальной переписки, скрыв ключ доступа и личные данные.
